# Возможности Pomen

## Обзор

Pomen — плагин Intermasq для выдачи доменных имен контейнерам Podman, запущенным через Quadlet внутри виртуальных машин. Работает по принципу **on-demand pull**: сеть не грузится фоновыми опросами, всё происходит по клику администратора.

---

## Управление реестром ВМ

- **CRUD через UI:** добавление, удаление и просмотр ВМ с Podman прямо в веб-интерфейсе. Никаких правок файлов на сервере.
- **Динамический реестр:** ВМ-ы хранятся в `vms.json` (отдельно от статического `config.json`). Короткоживущие ВМ легко добавлять и удалять.
- **Уникальность имен:** попытка добавить ВМ с уже существующим именем обновит её настройки (ip, webhook, секрет), а не создаст дубль.
- **Изоляция по нодам:** каждая ВМ привязана к ноде из `config.json` — это определяет, в какой Caddy будут писаться маршруты.
- **Безопасное удаление:** при удалении ВМ из реестра её маршруты в Caddy и `routes.json` **остаются** (offline) — очистка только вручную через вкладку «Маршруты». Защита от случайной потери выданных доменов при пересоздании ВМ.

## Обнаружение контейнеров (on-demand)

- **Кнопка «Обновить»:** плагин стучится на вебхук ВМ (`POST /hooks/podman` с заголовком `X-VM-Secret`), вебхук исполняет `podman ps --format json` и возвращает JSON.
- **Без фонового опроса:** между кликами сеть молчит. Нулевой шум, нулевые SSH-сессии, нулевые ключи на сервере плагина.
- **Парсинг реального вывода Podman:**
  - Имя: из `Names[0]` с обрезкой префикса `systemd-` и нумерации (`systemd-01-athens` → `athens`).
  - Порт: из `Ports[0].host_port` (надёжнее, чем ручные labels).
  - Статус: из `State`/`Status` — 🟢 для running, ⚫ для остановленных.
- **Labels переопределяют всё:** если в `.container` прописаны `Label=name-…`, `Label=port-…`, `Label=proto-…` — они имеют приоритет над автоопределением.

## Выдача доменов (Provision)

- **FQDN по схеме:** `<container>.<vm>.<node>.internal` (например `athens.obshaga.yadr00.internal`). Имя узла всегда в домене — никакой путаницы при десятках ВМ.
- **Caddy reverse_proxy:** маршрут пишется в Admin API Caddy соответствующей ноды (`POST /config/apps/http/servers/srv0/routes`).
- **TLS от Step-CA:** автоматически создаётся TLS-политика с ACME-челленджем против внутреннего Step-CA. Самоподписные сертификаты отключены глобально.
- **Idempotent upsert:** повторный Provision того же контейнера не создаёт дубль TLS-политики — используется `upsertByID` (PUT для существующих, POST для новых) вместо слепого POST. Решает ошибку Caddy `cannot apply more than one automation policy to host`.
- **The Nuke:** после применения маршрута плагин отправляет `POST /stop` в Caddy. Systemd (`Restart=always`) поднимает его через секунду — Caddy перечитывает `autosave.json` и берёт свежий сертификат, забыв плохой кэш.
- **Идемпотентные ID:** маршрут `pod-<vm>-<name>-<node>`, TLS `podtls-<vm>-<name>-<node>`. Гарантированно не конфликтует с `proxy-<VMID>-…` из Povez при общем Caddy.

## Маршруты и состояние

- **Таблица маршрутов:** все выданные домены в одном списке (вкладка «Маршруты») — domain, VM, IP, port, proto, node, время последнего обновления.
- **Offline-записи держатся:** если контейнер остановлен или ВМ умерла — запись в таблице остаётся. Автоматической очистки нет.
- **Ручная очистка:** кнопка 🗑️ напротив любой записи удаляет маршрут и TLS-политику из Caddy + запись из `routes.json`. Без проверки статуса контейнера — удаление по факту решения админа.
- **Replay Caddy:** кнопка «Replay» перезаписывает конфиг Caddy из файла-таблицы (`routes.json`) через upsert, затем один `/stop` на каждую затронутую ноду. Использовать после жёсткого сброса Caddy или при миграции.

## Безопасность

- **Rootless выполнение:** плагин работает как дочерний процесс `intermasq.service` от имени непривилегированного пользователя `intermasq`. Прав только на свою папку и сокет.
- **Unix-сокет:** связь с Intermasq через `/run/intermasq/sockets/pomen.sock` (0770). Никаких открытых TCP-порттов плагина.
- **Секрет per-VM:** каждый вебхук ВМ защищён своим секретом в заголовке `X-VM-Secret`. Секреты хранятся только в `vms.json` с правами `0660` владельца `intermasq`.
- **Нет SSH-ключей:** плагин не ходит на ВМ по SSH. Все запросы — исходящий HTTP от плагина к вебхуку ВМ. Утечка SSH-ключей физически невозможна — их нет.
- **HMAC на вебхуке:** вебхук ВМ (adnanh/webhook) сверяет `X-VM-Secret` до выполнения команды. Неавторизованные запросы не доходят до `podman`.

## Пользовательский опыт

- **Один бинарь:** бэкенд Go + фронтенд Vue 3 (один `index.html`) в одном файле ~10 МБ. Не требует Python, PHP, веб-сервера.
- **Три вкладки UI:** «Виртуальные машины» (CRUD), «Контейнеры» (обнаружение + выдача доменов), «Маршруты» (состояние + очистка + Replay).
- **Темная тема:** Bootstrap 5 с `data-bs-theme="dark"`.
- **Живой статус контейнеров:** 🟢/⚫ в списке контейнеров по реальному `State` из `podman ps`.
- **Защита от ошибок:** кнопка «Выдать домен» disabled, если у контейнера не определён порт. Нельзя выдать домен без upstream-порта.

## Интеграция с инфраструктурой

- **Intermasq ядро не трогается:** DNS-записи per-контейнер не пишутся. В dnsmasq один wildcard `address=/.node.internal/CADDY_IP` — маршрутизацию по Host-header делает Caddy.
- **Сосуществование с Povez:** оба плагина пишут в один Caddy, но с разными префиксами `@id` (`pod-` vs `proxy-`). Маршруты не затирают друг друга.
- **GitOps-совместимость:** labels в `.container` файлах тянутся через репозиторий (Quadlet). Сам плагин не модифицирует файлы на ВМ.
- **Шаблон webhook-deploy:** `pomen-hooks.json` деплоится через CI аналогично `hooks.json` (envsubst + SCP), без ручного вмешательства на ВМ.
